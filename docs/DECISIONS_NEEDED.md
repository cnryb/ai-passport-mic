## 1. KI-006 欠载的修法（最高优先，阻塞 G2）

### 现状（根因已定位，2026-11-07）

`G2` 要求"连续 10 min 0 欠载"，现在**FAIL**。但问题不再是"不知道为什么会欠载"。

真机四轮数据（600 s / 180 s / 180 s / 60 s，外加一轮 `--tone` 对照）：

| 指标 | 读数 | 结论 |
| --- | --- | --- |
| 块率 | **50.000 /s**（零误差） | 数据一块不少 |
| 序号跳变 / 长度异常 / 设备丢弃 | **0 / 0 / 0** | 链路没丢包 |
| **块到达间隔最大值** | **120.4 / 179.8 / 119.6 / 148.7 ms** | **抖动远大于 80 ms 缓冲上限** |
| 超过 80 ms 的迟到次数 | 100 / 113 / 86 / 43 | 与欠载次数（14/15/12/4）**强相关** |
| `--tone` 对照（精确 20 ms 配速，不连设备） | **运行期 0 欠载** | **声卡侧本身是干净的** |

**一句话根因：数据来的"总量"没问题，来的"时刻"不均匀；个别间隔超过 80 ms 缓冲上限，
缓冲被抽空就欠载一次。**

### 这个结论是怎么排除掉其他可能的

- 不是声卡回调停摆：`--tone` 下回调间隔稳定在 30–50 ms、最大 64 ms，0 欠载。
- 不是漂移控制器误补偿：2026-11-06 已修（墙钟法），现在报告漂移恒为 0 ppm、删音频 0。
- 不是喂入端拖后腿：`--tone` 实时率 1.000×、最大喂入间隔 30 ms。
- 不是块率不足：50.000 块/秒，精确到三位小数。

顺带修掉了 `--tone` 自己的两个测量 bug（原来会报 605 次假欠载），现在它是个可信的对照组。

### 需要你选的三条路

| | 方案 | 预期效果 | 代价 / 风险 |
| --- | --- | --- | --- |
| **A（推荐）** | 抬缓冲上限 80 → **150 ms** | 能盖住观察到的 100–120 ms 尖峰 | 端到端延迟 +70 ms，与 `p95 ≤ 150 ms` 的预算冲突；180 ms 那次仍会漏 |
| **B** | 改 BLE 连接参数（更小 interval / 更长 peripheral latency） | 从源头减少到达抖动，延迟不变 | 功耗上升；固件 6 个连接参数的退避逻辑要重验；可能触发 `LINK_SLOW` |
| **C** | `Playout` 加"抖动感知"自适应 | 抖动大时临时多存、平稳时收回，延迟动态 | 要重写自适应控制器。**有前车之鉴**：2026-11-06 那次"按存量驱动漂移补偿"就是这么写坏的，删了 39347 帧真实音频 |
| **D** | 接受现状，把 G2 判据从"0 欠载"改成"每分钟 ≤ N 次且单次 ≤ X ms" | 不改代码，立刻能关闭 G2 | 等于承认做不到 0 欠载；需要你定 N 和 X |

我倾向 **A + 后续再评估 B**：A 能在一天内做完且可自动验证（`./scripts/test-longrun.sh`），
B 需要动固件、周期更长。但 **A 会让延迟预算失效**，这是产品取向问题，不该由我定。

**注意：A/B/C 都要求先改 [`ARCHITECTURE.md`](ARCHITECTURE.md) 的延迟预算，再改代码。**

## 2. G2 判据本身要不要改

接上一条。现在的判据是"连续 10 min，**欠载 = 0**、静音帧 = 0"。
但真机四轮下来，链路侧所有指标都是满分，只有这一条过不去。

这可能是**判据过于理想**——虚拟声卡 + 非实时宿主（普通 macOS 桌面，不是 RT 内核）上，
"10 分钟一次都不欠"本身可能不现实。业界常见做法是"每分钟 ≤ 1 次、单次 ≤ 20 ms"。

**你的选择：** ☐ 保持"必须为 0" ☐ 改成阈值型（阈值：每分钟 ≤ ___ 次，单次 ≤ ___ ms）
