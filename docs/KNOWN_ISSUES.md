## KI-001：采集端满量程毛刺的根因未定位

**发现时间**：2026-11-04 首轮真机录音。

### 现象

6 次真机录音里有 2 次，在录音进行到 **7.7–8.5 s** 附近出现约 **0.8 s** 的 ±32767
逐样本变号噪声。同一次录音里 `序号跳变丢失 = 0`，即**不是丢块**、不是块头失配。

### 已经排除的

| 假设 | 怎么排除的 |
| --- | --- |
| ADPCM 编码器进入死循环状态 | 把同样的波形喂给 编码→解码：最多污染相邻 1–2 块，之后在静音和低电平底噪下都能自行收敛（`desktop/crates/protocol/tests/glitch_repro.rs` 固化） |
| 丢块导致块头失配 | 同次录音 `序号跳变 = 0`；且解码器每块由块头重置，丢块不会污染后续 |
| 麦克风真实削波 | 削波是平顶、同号连续；这段是逐样本变号（等价 ≥8 kHz 满量程方波），人声与室内噪声做不出这个形状 |
| 断连/重连导致的缓冲残留 | 现象发生在连续录音中段，链路未断，`record` 的丢块与长度异常两项均未增加 |

结论：数据在**进 ADPCM 之前**就已经是垃圾，问题在采集链路（I2S / ES8311）。

### 现在的拦截（不是修复）

两端各拦一次，保证"垃圾不出去"，**但没有解释垃圾为什么产生**：

- **固件**：编码前 `apm_pcm_is_corrupt()` 体检，命中就把整块压成静音并复位预测状态，
  只打串口日志、计数留在设备内存里。
- **PC**：解码后 `apm_protocol::glitch::Suppressor` 再兜一层（静音替换 + 64 样本淡入），
  `record` / `sink` 都过，收尾报告打印"采集端毛刺 N 段，已静音 M 帧"。
- **分析**：`apmctl analyze` 用同一判据扫描，出现即判 `software-fail`，JSON 带
  `glitch_events` / `glitch_ms`。判据口径见 [`SOUND_QUALITY.md`](SOUND_QUALITY.md) 的「毛刺」。

### 仍然未知的

1. **为什么 I2S/ES8311 会读出满量程变号数据。** 候选假设（都还没有证据）：
   codec 时钟瞬态、I2S DMA 半满回调错位或读越界、ES8311 内部软复位、供电跌落导致
   codec 重同步。7.7 s 这个位置是否与某个周期性事件（BLE 连接事件 30 ms、STATUS 心跳 1 s、
   或一次未记录的 gain 写入）对齐，也没查过。
2. **固件压掉的块数没上报。** 只进串口日志，STATUS 载荷仍是 8 字节。要上报得改协议
   （8 → 10 字节）、同步 `ARCHITECTURE.md`、重新生成两端向量。当时判断不值得为诊断字段
   改协议，所以没做 —— 这是取舍，不是遗漏。
3. **真机上出现频率**未知：2/6 是样本太小，没法判断是"偶发"还是"每 8 秒必现"。

### 下一步怎么查（可执行）

1. **抓编码前的原始 I2S 数据。** 在 `audio.c` 的读回调里留一个 100 ms 环形缓冲
   （16 kHz × 4 B × 0.1 s = 6.4 KB，设备无 PSRAM 也放得下），用 `apm_pcm_is_corrupt()`
   命中作为触发，把命中前的快照 + `i2s_channel_read` 返回值 + `esp_timer` 微秒时间戳
   一起输出到串口。这能直接回答"是数字侧还是模拟侧"。
2. **对齐时间轴。** 把抓到的时间戳与 STATUS 心跳、连接事件、按键事件对一遍，
   看毛刺是否总在某个固定周期后出现。
3. **改增益做对照。** 把 PGA 增益降 12 dB 跑 10 分钟：若毛刺仍满量程，更像数字侧
   （DMA / 时钟）；若随增益变小，指向模拟前端或供电。
4. **怀疑 codec 就 dump 寄存器。** 毛刺前后各读一遍 ES8311 的 0x00–0x45，看有没有
   软复位标志或时钟丢失。
5. **统计频率。** 连续 10 分钟录音，记录命中次数与间隔分布，把"2/6"这种样本量补到有意义。

### 验收标准

连续 10 分钟 `apmctl record`：

- `glitch_events == 0`，且串口日志里 `corrupt block` 计数为 0；
- `序号跳变丢失 == 0`；
- 在抓到根因之前，**只允许**在文档里写"已拦截"，不允许写"已解决"。

## KI-002：漂移补偿与毛刺拦截未真机复测

**代码**：`desktop/crates/sink/src/playout.rs`（漂移）、`apm_protocol::glitch`（毛刺）
＋ 固件 `apm_pcm_is_corrupt`。

**已有证据**：

- 漂移：仿真 60 s，−4200 ppm 与 +5000 ppm 两个方向均 0 欠载 / 0 超容量丢弃，
  存量稳定在 61.7 / 79.9 ms，ppm 估计误差 < 400。
- 毛刺：`crates/protocol` 单测 + 合成 WAV（1 段 / 799.6 ms 被正确识别并判 fail）。

**缺的证据**：真机。需要**重新烧录固件**（`apm_pcm_is_corrupt` 在固件侧）后跑：

```bash
./scripts/apmctl-macos.sh sink --to "BlackHole" --seconds 60
```

看收尾两行：

- `漂移: 补偿 ±xxx ppm（补样本 a / 丢样本 b）` —— ppm 应当在 ±5000 以内，
  且 `补/丢` 的样本数与 ppm × 时长对得上；
- `采集端毛刺: N 段 …` —— 若仍出现，说明拦截生效但根因（KI-001）还在。

`缓冲: 目标 …` 那行的欠载次数应为 0（暖机期除外）。

### 2026-11-05 真机复测（60 s，已烧新固件）

| 指标 | 实测 | 判据 |
| --- | --- | --- |
| 块数 / 序号跳变 / 长度异常 | 2998 / 0 / 0 | 丢块应为 0 |
| 声卡欠载 / 静音帧 / 超容量丢弃 | 0 / 0 / 0 | 欠载 0 |
| 时钟漂移补偿 | **−57 ppm**（补 1805 / 丢 1750 样本） | ±5000 ppm 内 |
| 缓冲存量 | 55–95 ms（目标 80） | 不触底、不超容量 |
| 采集端毛刺 | **0 段**（`glitch_events>0` 才会打印那行，这轮没打印） | KI-001 口径是 10 min |

结论：**60 s 干净**，漂移补偿方向与量级都对（设备时钟比声卡慢约 57 ppm）。
但这**不等于 KI-001 的验收已过** —— 它的口径是连续 10 min，且毛刺原本是 6 次里 2 次的
低频事件，60 s 采不到不能反证"不再出现"。10 min 那次见下。

### 2026-11-05 真机 10 min（KI-001 的正式口径）

先 `esptool --after hard_reset` 复位设备（理由是 KI-005），再跑
`apmctl sink --to "BlackHole" --seconds 600`：

| 指标 | 实测 | 判据 | 结论 |
| --- | --- | --- | --- |
| 块数 | 29998 / 600 s = 50/s | 50/s | PASS |
| 序号跳变丢失 / 长度异常 | 0 / 0 | 0 | PASS |
| 设备侧丢弃 | 0（复位后归零） | 0 | PASS |
| 采集端毛刺 | **0 段**（`glitch_events == 0`，那行没打印） | 0 | **PASS** |
| 声卡欠载 | **10 次**（763 静音帧 ≈ 48 ms） | 0 | **FAIL**（见 KI-006） |
| 漂移补偿 | +86 ppm（补 17707 / 丢 18535 样本） | ±5000 ppm 内 | PASS |

**KI-001 的两条验收（毛刺 0 段、序号跳变 0）在 10 min 上过了**，但这只能说明"这 10 分钟没再采到
垃圾数据"，**根因仍未定位**（串口里 `corrupt block` 计数没抓）。别写成"KI-001 已解决"。

## KI-003：没有声学回环，所以端到端延迟仍无数字

**已经有的**：`apmctl ping`（控制帧 `0x04 PING` / `0x83 PONG`）能测**链路往返时延**，
含两端协议栈、连接间隔、设备任务调度。

**2026-11-05 真机首次测量**（新固件，`ping --count 20`）：

| 指标 | 数值 |
| --- | --- |
| 发出 / 收到 / 超时 | 20 / 20 / 0 |
| 最小 / 中位 / p95 / 最大 | 35.4 / **38.2** / **41.5** / 57.9 ms |
| 相邻 RTT 平均绝对差（抖动） | 3.0 ms |
| 音频单程估计（中位 RTT/2） | ≈ 19.1 ms，**仅链路** |

38.2 ms 这个量级与 30 ms 连接间隔吻合（一个连接事件对 + 两端调度）。注意 #1 是 57.9 ms，
首次测量带着连接建立后的冷态，统计时把它算进 p95 之前要先看样本量——20 个样本的 p95
基本等于次大值，别当稳态分布用。

**仍然没有的**：真正的端到端声学延迟 = 声源 → 麦克风 → codec 采集 → 20 ms 分块 →
BLE → 抖动缓冲 → 声卡播放 → 扬声器。PING/PONG 只覆盖其中"BLE + 两端协议栈"这一段，
**不能**用它替代 M4 的 p95 结论。按 19.1 ms 单程 + 20 ms 分块 + 80 ms 目标缓冲粗算，
端到端大概率在 100–130 ms 区间，但这只是算术，不是测量。

**为什么卡住**：`sink --verify` 的回环需要宿主进程有麦克风权限；裸二进制会被 TCC 直接
abort，`apmctl-macos.sh` 的 `.app` 身份目前只声明了蓝牙用途。解法是 G3b：用 GUI 自身的
bundle 身份做回环验收（见 [`GUI.md`](GUI.md)）。

**临时折中**：用外接设备放一段已知脉冲（手机播 1 kHz 短音）录进 WAV，手工对时间轴。
只能给数量级，不能当验收数据。

## KI-004：cpal 钉在 0.15，`Stream: !Send` 是被迫的设计约束

**现象**：`apm-sink` 依赖 `cpal = "0.15"`。在这个版本里 `cpal::Stream` 是
`!Send`（`platform::NotSendSyncAcrossAllPlatforms`），因此声卡对象**只能**
在创建它的线程里活一辈子。

**现在的绕法**（`crates/app/src/session.rs`）：声卡独占一条命名 std 线程
（`apm-sink`），主线程通过 32 块有界 channel 喂 PCM，满了 `try_send` 丢块并计数。
这个绕法**本身是好的**（磁盘 IO 与声卡写入都不占 tokio worker），但它现在是
被迫的，不是选的。

**上游已经变了**：cpal 0.17.0 给 CoreAudio 的 `Stream` 加了 `Send`；
0.18 起 `DeviceTrait`/`StreamTrait` 把 `Send + Sync` 变成 supertrait。
0.17 还引入 `Device::id()`，能顺手修掉 `SinkInfo.uid` 目前"拿设备名当 ID"的问题。

**为什么还没升**：0.17/0.18 有一串破坏性改动 —— `SampleRate` 从 newtype 变 `u32` 别名、
`build_*_stream` 改为按值收 `StreamConfig`、**流不再自动 start**（要显式 `play()`）、
0.18 移除 `DeviceTrait::name()`、MSRV 抬到 1.85。这些都在**已验证能出声**的那条路径上，
不能顺手改。

**升级的判据**（不是时间表）：
1. 先让 `./scripts/test-sink.sh` 在升级前后各跑一次，结果一致；
2. `cargo test` 93 项全绿、GUI 能开流；
3. 真机（会议上当麦克风）复测一次。

**升级之后要不要拆掉那条声卡线程**：不一定要。即使 `Stream: Send`，让声卡独占线程
仍然能避免 BLE 突发把 tokio worker 顶住。届时它从"被迫"变成"选的"，这条 KI 就可以关掉。

## KI-005：设备异常断开后不会自己恢复到可采集状态

**发现时间**：2026-11-05 第二轮真机测试。

### 现象

块率从正常的 **50 块/秒**（20 ms 一块）掉到 **1.5–2 块/秒**，同时：

- `欠载` 每秒涨 ~30 次、`静音帧` 几十万（声卡在狂补静音）；
- `漂移` 一路跑到 −8000 ~ −9600 ppm（存量触底，控制器一直往一个方向拉）；
- `序号跳变丢失 = 0`、`长度异常 = 0` —— 不是丢包，是**设备几乎不发**。

| 时刻 | 操作 | 块数 | 欠载 | 设备侧丢弃 |
| --- | --- | --- | --- | --- |
| 11:1x | GUI 运行期间起 `apmctl sink` | 41 / 25 s ≈ 1.6/s | 638 | 1970 |
| 之后 | 关掉 GUI，15 s 重跑 | **750 / 15 s = 50/s** | 0 | 1970（累计值，见下） |
| 之后 | 600 s 长测第 1 次（21 s） | 36 ≈ 1.7/s | 537 | — |
| 之后 | 600 s 长测第 2 次（29 s） | 49 ≈ 1.7/s | 761 | — |
| 之后 | **esptool `--after hard_reset`** 后 20 s | **998 / 20 s = 50/s** | 0 | 0 |

### 判断

`apmctl` 进程被 `pkill`（异常路径）时 `CTRL STOP` 没送达，设备停在
`capturing` 但采集/发送已经停了的状态；下一条链路发 `CTRL START` 被当成"已经在采集"忽略，
于是只回状态、不发音频。**复位（`esptool --after hard_reset` 或拔插 USB）立刻恢复。**
这是推断，不是抓到根因——固件侧状态机对"链路断开但没收到 STOP"这条路径没有兜底。

### 第二种触发方式：连上之后迟迟不发 START（2026-11-05 G2 现场）

GUI 侧测 G2 时换了一条路径踩到同一个坑，值得单独记：

| 观察 | 数据 |
| --- | --- |
| 点「连接」后、点「开始」前，设备已经在发音频 | 诊断日志里 450 ms 内 16 条 `收到音频块 165 字节但当前未推流`，随后**自己停了** |
| 点「开始」后块率只有名义值的一半 | 约 **28 块/秒**（应 50/s）；`丢块 3498`、`跳变 3398` |
| 设备自己也在丢 | `设备丢弃 3992`（干净会话是 0） |
| 声卡侧连锁反应 | `欠载 6100`、`静音帧 1089273`、`缓冲` 掉到 20 ms、`漂移` 打到 −9997 ppm 下限 |
| 同样条件下 CLI 完全正常 | 复位后 `apmctl sink --seconds 30`：1498 块（50/s）、0 丢块、0 欠载、设备侧丢弃 0 |

**两个客户端的唯一差别是"连接 → START"的间隔**：CLI 连上立刻发 START（全程 0 条"未推流"告警）；
GUI 是连接、等用户点「开始」，中间隔了约 90 秒。设备在这段空窗里先是自己在推，
然后停住；等 START 再来时已经处在"半死"状态——推得动，但一直在丢。

**结论（假设，未在固件侧证实）**：设备对"连接后长时间不上报 START"没有超时兜底，
会停在一个既非 idle 也非正常采集的中间态；此时再 START 只恢复了一部分。
**规避**：GUI 若长时间停在 `ready` 不动，先复位设备再开始；PC 侧更该做的是在 `start_stream`
前发一次 `STOP` 把设备状态清干净。

### 影响

**这是做任何长测试前必须排除的干扰项。** 如果不复位就跑 10 min，会得到一份"欠载上千、
漂移 −9000 ppm"的报告，看起来像漂移补偿或声卡出了问题，实际是设备没在发数据。
本轮有两次 600 s 尝试就是这样作废的。

### 下一步（任意一条都能收口）

1. 固件侧：链路断开（`BLE_GAP_EVENT_DISCONNECT`）时强制回到 idle 并停 I2S，不等 STOP；
2. PC 侧：`sink` / `record` 开流后若 2 s 内块数 < 10，直接报"设备未开始发送，建议复位设备"，
   不要继续跑出一份脏报告；
3. 至少在 `--seconds` 长测前加一句"先复位"，写进脚本而不是靠人记。

### 附带发现：`设备侧丢弃` 是累计值，不是本会话值

`crates/app/src/pipeline.rs` 的 `on_status` 直接 `device_dropped = status.dropped`，
而设备这个计数**自设备启动起单调累加**。所以一次干净会话也可能报出"设备侧丢弃 1970"
（那是上一次坏会话留下的）。看这个数要**跨会话做差**，不能直接当本次丢失数读。

## KI-006：10 min 长测里有 10 次声卡欠载

**发现时间**：2026-11-05 真机 10 min 长测（KI-001 验收那一跑）。

### 现象

29998 块、序号跳变 0、长度异常 0、设备侧丢弃 0、毛刺 0 段 —— **链路和采集都是干净的**，
但 `声卡: 欠载 10 次（静音 763 帧 ≈ 48 ms）`，单次约 4.8 ms。

欠载发生的秒数（从日志逐行抽出）：**216 / 299 / 399 / 418 / 422 / 579 / 581 / 582(×2) / 594**。
散在全程，**不是暖机期**，也不与任何已知周期（STATUS 心跳 1 s、连接事件 30 ms）对齐。

### 已经排除的

| 假设 | 依据 |
| --- | --- |
| 设备没发 / 发慢了 | 块数 29998 恰好等于 600 s × 50/s；序号 0 跳变 |
| 通道满丢块 | `通道满丢块 0`、`超容量丢弃 0` |
| 锁竞争 | `回调抢锁失败 0 次` |
| 缓冲目标设小了 | 目标本来就在上限 80 ms，无余量可调 |
| 暖机期的一次性 | 第一次欠载在 216 s，最后一次在 594 s |

### 候选原因（都还没验）

1. **声卡回调被系统抢占**：Mac 上有其他 App 占用 CoreAudio 时，cpal 的回调可能晚于预期；
2. **漂移控制器在 ppm 过零附近插删偏激进**：欠载前后 ppm 从 −48 走到 +74 再回落，
   控制环在零附近来回修正时可能让存量瞬时跌破下限（`crates/sink/src/playout.rs`）；
3. `coreaudiod` 自身的重采样/时钟补偿（BlackHole 是虚拟设备，其时钟由驱动提供）。

### 影响

- **G2 的验收口径是"连续 10 min：0 欠载、0 静音帧"，这一条现在不通过**，交付时只能写
  "10 次欠载 / 48 ms 累计静音"，不能写"零欠载"。
- 实际听感上 48 ms 分布在 10 分钟里，会议里基本听不出来——但这是判断，不是指标。
