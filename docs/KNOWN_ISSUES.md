## KI-001：采集端满量程毛刺的根因未定位

**发现时间**：2026-11-04 首轮真机录音。

### 现象

6 次真机录音里有 2 次，在录音进行到 **7.7–8.5 s** 附近出现约 **0.8 s** 的 ±32767
逐样本变号噪声。同一次录音里 `序号跳变丢失 = 0`，即**不是丢块**、不是块头失配。

### 已经排除的

| 假设 | 怎么排除的 |
| --- | --- |
| ADPCM 编码器进入死循环状态 | 把同样的波形喂给 编码→解码：最多污染相邻 1–2 块，之后在静音和低电平底噪下都能自行收敛（`desktop/crates/protocol/tests/glitch_repro.rs` 固化） |
| 丢块导致块头失配 | 同次录音 `序号跳变 = 0`；且解码器每块由块头重置，丢块不会污染后续 |
| 麦克风真实削波 | 削波是平顶、同号连续；这段是逐样本变号（等价 ≥8 kHz 满量程方波），人声与室内噪声做不出这个形状 |
| 断连/重连导致的缓冲残留 | 现象发生在连续录音中段，链路未断，`record` 的丢块与长度异常两项均未增加 |

结论：数据在**进 ADPCM 之前**就已经是垃圾，问题在采集链路（I2S / ES8311）。

### 现在的拦截（不是修复）

两端各拦一次，保证"垃圾不出去"，**但没有解释垃圾为什么产生**：

- **固件**：编码前 `apm_pcm_is_corrupt()` 体检，命中就把整块压成静音并复位预测状态，
  只打串口日志、计数留在设备内存里。
- **PC**：解码后 `apm_protocol::glitch::Suppressor` 再兜一层（静音替换 + 64 样本淡入），
  `record` / `sink` 都过，收尾报告打印"采集端毛刺 N 段，已静音 M 帧"。
- **分析**：`apmctl analyze` 用同一判据扫描，出现即判 `software-fail`，JSON 带
  `glitch_events` / `glitch_ms`。判据口径见 [`SOUND_QUALITY.md`](SOUND_QUALITY.md) 的「毛刺」。

### 仍然未知的

1. **为什么 I2S/ES8311 会读出满量程变号数据。** 候选假设（都还没有证据）：
   codec 时钟瞬态、I2S DMA 半满回调错位或读越界、ES8311 内部软复位、供电跌落导致
   codec 重同步。7.7 s 这个位置是否与某个周期性事件（BLE 连接事件 30 ms、STATUS 心跳 1 s、
   或一次未记录的 gain 写入）对齐，也没查过。
2. **固件压掉的块数没上报。** 只进串口日志，STATUS 载荷仍是 8 字节。要上报得改协议
   （8 → 10 字节）、同步 `ARCHITECTURE.md`、重新生成两端向量。当时判断不值得为诊断字段
   改协议，所以没做 —— 这是取舍，不是遗漏。
3. **真机上出现频率**未知：2/6 是样本太小，没法判断是"偶发"还是"每 8 秒必现"。

### 下一步怎么查（可执行）

1. **抓编码前的原始 I2S 数据。** 在 `audio.c` 的读回调里留一个 100 ms 环形缓冲
   （16 kHz × 4 B × 0.1 s = 6.4 KB，设备无 PSRAM 也放得下），用 `apm_pcm_is_corrupt()`
   命中作为触发，把命中前的快照 + `i2s_channel_read` 返回值 + `esp_timer` 微秒时间戳
   一起输出到串口。这能直接回答"是数字侧还是模拟侧"。
2. **对齐时间轴。** 把抓到的时间戳与 STATUS 心跳、连接事件、按键事件对一遍，
   看毛刺是否总在某个固定周期后出现。
3. **改增益做对照。** 把 PGA 增益降 12 dB 跑 10 分钟：若毛刺仍满量程，更像数字侧
   （DMA / 时钟）；若随增益变小，指向模拟前端或供电。
4. **怀疑 codec 就 dump 寄存器。** 毛刺前后各读一遍 ES8311 的 0x00–0x45，看有没有
   软复位标志或时钟丢失。
5. **统计频率。** 连续 10 分钟录音，记录命中次数与间隔分布，把"2/6"这种样本量补到有意义。

### 验收标准

连续 10 分钟 `apmctl record`：

- `glitch_events == 0`，且串口日志里 `corrupt block` 计数为 0；
- `序号跳变丢失 == 0`；
- 在抓到根因之前，**只允许**在文档里写"已拦截"，不允许写"已解决"。

## KI-003：没有声学回环，所以端到端延迟仍无数字

**已经有的**：`apmctl ping`（控制帧 `0x04 PING` / `0x83 PONG`）能测**链路往返时延**，
含两端协议栈、连接间隔、设备任务调度。

**2026-11-05 真机首次测量**（新固件，`ping --count 20`）：

| 指标 | 数值 |
| --- | --- |
| 发出 / 收到 / 超时 | 20 / 20 / 0 |
| 最小 / 中位 / p95 / 最大 | 35.4 / **38.2** / **41.5** / 57.9 ms |
| 相邻 RTT 平均绝对差（抖动） | 3.0 ms |
| 音频单程估计（中位 RTT/2） | ≈ 19.1 ms，**仅链路** |

38.2 ms 这个量级与 30 ms 连接间隔吻合（一个连接事件对 + 两端调度）。注意 #1 是 57.9 ms，
首次测量带着连接建立后的冷态，统计时把它算进 p95 之前要先看样本量——20 个样本的 p95
基本等于次大值，别当稳态分布用。

**仍然没有的**：真正的端到端声学延迟 = 声源 → 麦克风 → codec 采集 → 20 ms 分块 →
BLE → 抖动缓冲 → 声卡播放 → 扬声器。PING/PONG 只覆盖其中"BLE + 两端协议栈"这一段，
**不能**用它替代 M4 的 p95 结论。按 19.1 ms 单程 + 20 ms 分块 + 80 ms 目标缓冲粗算，
端到端大概率在 100–130 ms 区间，但这只是算术，不是测量。

**为什么卡住**：`sink --verify` 的回环需要宿主进程有麦克风权限；裸二进制会被 TCC 直接
abort，`apmctl-macos.sh` 的 `.app` 身份目前只声明了蓝牙用途。解法是 G3b：用 GUI 自身的
bundle 身份做回环验收（见 [`GUI.md`](GUI.md)）。

**临时折中**：用外接设备放一段已知脉冲（手机播 1 kHz 短音）录进 WAV，手工对时间轴。
只能给数量级，不能当验收数据。

## KI-004：cpal 已从 0.15 升到 0.18.2（`Stream: !Send` 的约束已消除）

**现象**：`apm-sink` 依赖 `cpal = "0.15"`。在这个版本里 `cpal::Stream` 是
`!Send`（`platform::NotSendSyncAcrossAllPlatforms`），因此声卡对象**只能**
在创建它的线程里活一辈子。

**现在的绕法**（`crates/app/src/session.rs`）：声卡独占一条命名 std 线程
（`apm-sink`），主线程通过 32 块有界 channel 喂 PCM，满了 `try_send` 丢块并计数。
这个绕法**本身是好的**（磁盘 IO 与声卡写入都不占 tokio worker），但它现在是
被迫的，不是选的。

**上游已经变了**：cpal 0.17.0 给 CoreAudio 的 `Stream` 加了 `Send`；
0.18 起 `DeviceTrait`/`StreamTrait` 把 `Send + Sync` 变成 supertrait。
0.17 还引入 `Device::id()`，能顺手修掉 `SinkInfo.uid` 目前"拿设备名当 ID"的问题。

**为什么还没升**：0.17/0.18 有一串破坏性改动 —— `SampleRate` 从 newtype 变 `u32` 别名、
`build_*_stream` 改为按值收 `StreamConfig`、**流不再自动 start**（要显式 `play()`）、
0.18 移除 `DeviceTrait::name()`、MSRV 抬到 1.85。这些都在**已验证能出声**的那条路径上，
不能顺手改。

**升级的判据**（不是时间表）：
1. 先让 `./scripts/test-sink.sh` 在升级前后各跑一次，结果一致；
2. `cargo test` 93 项全绿、GUI 能开流；
3. 真机（会议上当麦克风）复测一次。

**升级之后要不要拆掉那条声卡线程**：不一定要。即使 `Stream: Send`，让声卡独占线程
仍然能避免 BLE 突发把 tokio worker 顶住。届时它从"被迫"变成"选的"，这条 KI 就可以关掉。

### 2026-11-06 23:0x 已升级到 cpal 0.18.2

按上面的判据执行，三项全过：

| 判据 | 结果 |
| --- | --- |
| 1. `./scripts/test-sink.sh` 升级前后各跑一次，结果一致 | **PASS**（升级前 PASS、升级后 PASS，都是"声卡打开/写入/收尾都通了"） |
| 2. `cargo test` 全绿 | **PASS**：130 passed / 0 failed / 2 ignored（升级当时；2026-11-07 复核同为 **130 passed / 2 ignored**，见 `desktop/README.md`） |
| 3. 真机复测 | **PASS**，见下表 |

#### 改了什么

| 破坏性改动 | 处理 |
| --- | --- |
| `SampleRate` newtype → `u32` 别名 | 去掉所有 `.0`；`cpal::SampleRate(rate)` → 直接 `rate` |
| `build_*_stream` 按值收 `StreamConfig` | `let config = *config;`（0.18 里它是 `Copy`） |
| 流不再自动 start | 原本就显式调了 `stream.play()`，无需改 |
| 0.18 移除 `DeviceTrait::name()` | 改用 `device.description()?.name()` |
| — | **顺带修好 `SinkInfo.uid`**：以前拿设备名当 ID，现在用 `device.id()`（CoreAudio 的 UID 字符串）。两块同型号 USB 声卡不会再被认成一个 |

#### `Stream: Send` 已落实

加了一条编译期断言，防止将来有人把 cpal 降回旧版本又悄悄丢掉这个能力：

```rust
#[test]
fn cpal_stream_is_send() {
    fn assert_send<T: Send>() {}
    assert_send::<cpal::Stream>();
}
```

**但那条声卡线程先留着**：它现在从"被迫"变成"选的"——即使 `Stream` 能跨线程，
让声卡独占一条命名 std 线程仍能避免 BLE 突发把 tokio worker 顶住。
按 KI-004 原文的判断，这是更好的设计，不是需要拆掉的历史包袱。

#### 顺带发现并修掉的一处参数冲突

守卫刚落地时缓冲长期偏高（中位 117 ms、13 个整秒 >150 ms）。原因是
`can_lower()` 要求"存量 > 目标 + 20 ms"才肯把目标降一档，而守卫修剪保留的余量
只有 +10 ms —— **修剪得比门槛还低，目标就只升不降**。

调参过程（每轮 90 s）：

| `TRIM_OVER_MS` / `TRIM_BACK_MS` | 欠载 | 静音帧 | 缓冲中位 |

## KI-005：设备异常断开后不会自己恢复到可采集状态

**发现时间**：2026-11-05 第二轮真机测试。

### 现象

块率从正常的 **50 块/秒**（20 ms 一块）掉到 **1.5–2 块/秒**，同时：

- `欠载` 每秒涨 ~30 次、`静音帧` 几十万（声卡在狂补静音）；
- `漂移` 一路跑到 −8000 ~ −9600 ppm（存量触底，控制器一直往一个方向拉）；
- `序号跳变丢失 = 0`、`长度异常 = 0` —— 不是丢包，也**不是没采集**，是**发不出去**（见下）。

| 时刻 | 操作 | 块数 | 欠载 | 设备侧丢弃 |
| --- | --- | --- | --- | --- |
| 11:1x | GUI 运行期间起 `apmctl sink` | 41 / 25 s ≈ 1.6/s | 638 | 1970 |
| 之后 | 关掉 GUI，15 s 重跑 | **750 / 15 s = 50/s** | 0 | 1970（累计值，见下） |
| 之后 | 600 s 长测第 1 次（21 s） | 36 ≈ 1.7/s | 537 | — |
| 之后 | 600 s 长测第 2 次（29 s） | 49 ≈ 1.7/s | 761 | — |
| 之后 | **esptool `--after hard_reset`** 后 20 s | **998 / 20 s = 50/s** | 0 | 0 |

### 判断（2026-11-05 深夜修正，原判断作废）

原文写的是"`CTRL START` 被当成'已经在采集'忽略，于是只回状态不发音频"。
**这条不成立**：`s_forced_capture` 只是一个 bool，START 无条件置 true，代码里没有
"已采集就忽略"的分支。真正的问题是**发不出去**，不是**没在发**。

把第三种触发的数字对齐，指向很明确：

| 推理 | 依据 |
| --- | --- |
| 采集/编码循环全程按 50 块/秒在跑 | 298 s 丢 14322 块 + 收到约 600 块 ⇒ 序号推进 ≈14900 次 = **50/s**。序号只在编码成功、进 `notify` 之前自增 |
| 掉块发生在发送阶段，不是采集阶段 | 同一场 STATUS 的 `dropped` 同步涨到 14322 —— 那是 `apm_link_notify_audio()` 返回非 0 时累加的 |
| 链路吞吐上限 ≈2 块/秒 | 每 500 ms 才送出一块 —— 这是连接间隔在 500 ms 量级时的形状（不是丢包：跳变少、`长度异常 0`） |
| "6 块一组"是协议栈缓冲的粒度 | 一条音频通知占 2 个 msys 块（ATT 头 + 165 字节载荷），`MSYS_1_BLOCK_COUNT=12` ⇒ **6 条在途**；池满即 ENOMEM，腾出 6 块才再放 6 块 |

所以机理是：

> 主机没有接受 15–30 ms 的参数更新（固件只在建连瞬间请求一次，被拒就再也不提）→
> 连接间隔停在 500 ms 量级 → 吞吐掉到 ≈2 块/秒 → 通知把 msys 池打满 →
> 96% 的块丢在设备侧协议栈 → PC 看到"设备几乎不发"，欠载/漂移触底全是连锁反应。

自愈也解释得通：间隔被重新协商回快速档后，同一份代码立刻回到 50/s，与复位无关 ——
这正是"复位不保证恢复、不复位也可能恢复"的原因。

第一次触发里 `apmctl` 被 `pkill` 只是**诱发条件**（异常断开会打乱上一条会话的参数协商），
不是根因。而"断链不清 START"是另一个独立的真 bug：它让设备带着 `capturing` 进下一条链路，
第二、三种触发里的"连上就已在发音频""GUI 空窗 90 s 后半死"都被它放大。

### 第二种触发方式：连上之后迟迟不发 START（2026-11-05 G2 现场）

GUI 侧测 G2 时换了一条路径踩到同一个坑，值得单独记：

| 观察 | 数据 |
| --- | --- |
| 点「连接」后、点「开始」前，设备已经在发音频 | 诊断日志里 450 ms 内 16 条 `收到音频块 165 字节但当前未推流`，随后**自己停了** |
| 点「开始」后块率只有名义值的一半 | 约 **28 块/秒**（应 50/s）；`丢块 3498`、`跳变 3398` |
| 设备自己也在丢 | `设备丢弃 3992`（干净会话是 0） |
| 声卡侧连锁反应 | `欠载 6100`、`静音帧 1089273`、`缓冲` 掉到 20 ms、`漂移` 打到 −9997 ppm 下限 |
| 同样条件下 CLI 完全正常 | 复位后 `apmctl sink --seconds 30`：1498 块（50/s）、0 丢块、0 欠载、设备侧丢弃 0 |

**两个客户端的唯一差别是"连接 → START"的间隔**：CLI 连上立刻发 START（全程 0 条"未推流"告警）；

然后停住；等 START 再来时已经处在"半死"状态——推得动，但一直在丢。

**结论（2026-11-05 深夜修正）**：前半段"连上就自己在发"是**断链没清 START**（真 bug，

**当时的规避**（保留，现在只作兜底）：GUI 若长时间停在 `ready` 不动，先复位设备再开始；
PC 侧在 `start_stream` 前发一次 `STOP` 把设备状态清干净。

## KI-006：10 min 长测里有 10 次声卡欠载

> 状态：**根因已定位（2026-11-07 凌晨）——链路到达抖动突破 80 ms 缓冲上限**。

> 都要先改 `ARCHITECTURE.md` 的延迟预算。

> 只解决停摆（比如抬缓冲）最多缓解，`err` 的误判逻辑还在；只修控制器则要重新设计

#### 结论二（修正版）：不是"读数不准"，是**控制器真的在删真实音频**

> **本节最初写的机理是错的，2026-11-06 深夜已用仿真与真机对照推翻。**
> 当时写的是"欠载静音帧混进了 `(丢−补)`"，并据此认为"真实漂移只有 +7/+51/+25 ppm"。
> 那个结论**只在 22:24 那一轮碰巧成立**，换一轮就崩（见下面的实证）。

先看修正后的真相：`Playout::fill` 在每个 10 ms 回调开头算一次
`err = 现有帧数 − 目标帧数`，再按 `err / (rate × τ)` 给出每帧的插删速率。问题在于
**`push()` 在 `fill()` 之前**，所以每次 `fill` 看到的 `err` 都包含"本轮刚推进来的那 10 ms"。
只要这个 `err` 为正，控制器就认为"生产快于消费"，开始用 ±1% 删样本。

**仿真（精确复刻原实现）**——同速率、真漂移 = 0，只改变回调停摆频率：

| 场景 | 欠载 | 被删的真实音频 | 报告 ppm |
| --- | --- | --- | --- |
| 无停摆 | 0 | **0 帧** | **+0** |
| 每 10 s 停 1 拍 | 0 | 799 帧 | +834 |
| **每 3 s 停 1 拍** | 0 | **2834 帧（0.18 s）** | **+2964** |
| 每 3 s 停 2 拍 | 0 | 5662 帧（0.35 s） | +5940 |

**真机基线（2026-11-06 23:0x，40 s，原始代码）**：欠载 13 次、丢 2997 帧、补 792 帧，
报告 **3454 ppm**。落在"每 3 秒停 1–2 拍"这一档，**与仿真的形状一致**。

所以：

1. **无停摆时 `ppm` 是准的**（仿真 +0 vs 真值 +0；纯 +5000 ppm 读成 +4839）。
   我先前说"三轮独立验证"是错的——11-05 上午那轮丢−补 = −828（净补了 828 样本），
   静音只 763，比例完全对不上，那轮根本不支持那个说法；
2. **有停摆时控制器会真的删除真实音频**，然后把这个删除量如实记进 `frames_skipped`。
   `ppm` 报出数千，是**在如实报告"我丢了这么多帧"**——只不过它把这归因为"时钟差"，
   而归因是错的：那是消费端的停顿，不是生产端的漂移；
3. 因此这条**不是读数 bug，是控制逻辑 bug**，且会伤及音质（每次 CoreAudio 抖动
   吞掉 0.1–0.2 秒人声）。

#### 下一步该怎么做（留给下一轮）

问题的本质是**控制器分不清"存量高"是因为时钟快还是因为消费端刚停顿过**。可选方向：

1. **用生产侧的到达速率估计漂移**，而不是用缓冲存量。控制器只该看"每秒推入多少帧"，
   消费端停顿不该影响这个判断——这是最符合物理的方向；
2. 给 `err` 加**低通滤波 / 长时间窗**（现在 τ = 2 s 对 10 ms 级的停摆太敏感）；
3. `fill` 量 `err` 时扣掉本轮 `push` 的份额（仿真里能把纯速率场景修对，
   但停摆场景仍会 +1340 ppm，不够）；
4. 先修"停摆后丢旧数据、不积分"，再把裁剪量改成"只裁到目标 + 半死区"而非精确目标。

无论哪个方向，**验收必须包含**：真机 10 min 的欠载次数**不高于**原始实现的量级
（约 15–20 次/分），且 `丢−补` 与报告 ppm 同时下降。

#### ✅ 已修复（2026-11-06 深夜，真机 10 min 验证）

按方向 1 落地，**把"测漂移"和"处理停摆"彻底拆开**：

| 职责 | 新做法 | 为什么 |
| --- | --- | --- |
| 估计漂移 | `ppm = (pushed / (rate × 墙钟秒数) − 1) × 1e6` | 分子来自 BLE 推送（设备时钟）、分母来自系统墙钟，**两者都与声卡回调无关**，停摆期间读数纹丝不动 |
| 吸收停摆积压 | 存量 > 目标 + `TRIM_OVER_MS`(60 ms) 时一次性丢最旧的数据，回到目标 + `TRIM_BACK_MS`(35 ms) | 停摆堆起来的旧数据不该靠 ±1% 慢慢"补"几十秒，那期间一直在删真实音频。**参数是实测选的**（见 `playout.rs` 的对比表）：60/35 欠载最少；`back=30` 能把缓冲压到 87 ms 但欠载翻三倍 |
| 漂移补偿速率 | `= ppm/1e6`，**完全不看缓冲存量** | 旧实现用 `err = 存量 − 目标`，把消费端停顿误判成时钟差 |

**G2 仍应记为 FAIL，且不能写成"接近通过"。**

#### 2026-11-07 `--tone` 对照实验：声卡侧是干净的，问题在「块到达间隔」

之前所有轮次都带着 BLE 链路，所以"是不是链路抖动"一直只是推断。`apmctl sink --tone`
本来就是为了"只验声卡那一段"而写的（不连设备、直接推 440 Hz），正好拿来做对照。
**结论和预期相反，而且中间踩了两个测量坑，都记下来。**

**坑 1：`--tone` 自己的配速就错了。** 第一轮 180 s 报出 **605 次欠载**。算术一看就不对：

| 量 | 值 |
| --- | --- |
| 推入 | 2,880,000 帧 = **180.000 s** |
| 声卡取走 | 3,074,560 帧 = **192.160 s** |
| 差额 | **12.160 s** |
| 欠载补静音 | 605 × 320 帧 = 193,600 帧 = **12.100 s** |

差额 ≈ 补静音量，说明**声卡在正常消费，是喂入端喂不上**。根因是配速写成
"每 5 块 `sleep(100 ms)`"：一秒里睡满 1000 ms 之后还要**再加**生成 50 块的计算时间，
于是每秒都落后一点、越落越多（实测 ~6.7 ms/s）。
**已修**：改按绝对时刻配速（第 i 块在 `(i+1) × 20 ms` 前喂进去，落后就补、不落后才睡）。

**坑 2：把"收尾抽干"算成了运行期欠载。** 配速修好后仍读到 8 次欠载。加了"欠载时刻"记录
才看清：8 次全部在 **120032 / 120064 / … / 120256 ms**——即喂入刚结束后的那 300 ms
`sleep` 里。喂入一停，缓冲里剩的 80 ms 必然被抽干，抽干就欠载。
**已修**：统计在收尾等待**之前**取，收尾那段单独打印、不计入运行期。

**修完两个坑之后的结果**（同一台机器、同一个 80 ms 目标、同一块 BlackHole）：

| 跑法 | 时长 | **运行期欠载** | 实时率 | 最大喂入间隔 | 回调最大间隔 | 回调迟到(>1.5×) |
| --- | --- | --- | --- | --- | --- | --- |
| 带 BLE 的 10 min 长测 | 600 s | **48**（4.6/分） | 50.000 块/秒 | — | — | — |
| `--tone` ①（修完两坑） | 120 s | **0** | 1.000× | 30.0 ms | 32.1 ms | 0 |
| `--tone` ②（复跑） | 120 s | **0** | 1.000× | 34.3 ms | 64.1 ms | 2 |

**结论**：

1. **声卡侧完全干净**：实时喂入下运行期 0 欠载、回调间隔稳定在 30–50 ms。此前
   "CoreAudio 回调被系统停摆"的猜测**不成立**，可以从候选原因里划掉。
2. **所以差异只剩"数据从哪来"**：同样的声卡、同样的目标、同样的平均速率，
   带 BLE 就 4.6 次/分，纯软件喂入 0 次。
3. **但不能直接归因成"BLE 链路丢包"**——长测的丢块/跳变/设备丢弃全是 0。
   更可能的机制是**到达间隔的抖动**：`--tone` 按精确绝对时刻喂入（间隔几乎恒定），
   而真实路径的推送时刻由 BLE 通知决定，平均 50 块/秒但相邻间隔忽长忽短。
   目标缓冲已在上限 80 ms，自适应用完了余量（`target_raises` 抬不动），
   所以任何超过 80 ms 的到达间隔都会立刻造成一次欠载。

**下一步（可执行，不需要猜）**：在 `Pipeline` 里记录**相邻音频块的到达间隔**直方图，
与 `--tone` 的 30 ms 稳定值对比。

- 若 BLE 路径的到达间隔经常 > 80 ms → 根因是链路抖动超过缓冲上限，
  修法是抬上限（要先改 `ARCHITECTURE.md` 的延迟预算）或换连接参数；
- 若到达间隔正常却仍欠载 → 再回头查 `Pipeline` 到 `Playout` 这一段（含 channel 与锁）。

#### ✅ 根因已定位（2026-11-07 凌晨，真机两轮验证）

按上一条做完，答案出来了：**欠载来自链路到达抖动突破 80 ms 缓冲上限**。

`Pipeline::note_arrival` 记录每两个音频块的到达间隔，`sink` 收尾时打印直方图：

| 轮次 | 时长 | 块数 | 块率 | 最大到达间隔 | >80 ms 迟到 | 尖峰>100 ms | 欠载 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| ① | 179.96 s | 8998 | **50.000/s** | **120.4 ms** | 100 | 5 | 14 |
| ② | 179.94 s | 8998 | **50.000/s** | **179.8 ms** | 113 | 6 | 15 |

到达间隔分布（第 ① 轮）：`0–30ms: 7454`、`30–50ms: 836`、`50–60ms: 488`、`60–70ms: 119`、
`80–100ms: 95`、`100–200ms: 5`。

**这就解释了全部现象**：

1. **平均块率完美 50.000/s、序号跳变 0、设备丢弃 0** —— 数据一块不少，只是**来的时刻不均匀**。
   这也解释了为什么之前所有轮次都是"链路指标全绿、却仍有欠载"。
2. **缓冲目标已在上限 80 ms**：任何超过 80 ms 的到达间隔都直接吃掉存量。存量正好 80 ms 时，
   80–100 ms 的间隔就会欠载一次；存量更少时更早欠载。
3. **迟到次数（100）远多于欠载次数（14）是正常的**：存量接近目标时，80–100 ms 的间隔
   多数还能被吸收；只有更长的尖峰（>100 ms，两轮各 5 / 6 次）几乎必然造成欠载。
   所以**不能**用"迟到次数 vs 欠载次数"的比值判断对错。
4. **`--tone` 对照（0 欠载）与这里并不矛盾**：`--tone` 用 `sleep_until` 精确到
   `(i+1) × 20 ms` 喂入，间隔近乎恒定（最大 30 ms）；BLE 路径的推送时刻由通知到达决定，
   天然带抖动。**同一块声卡、同一个目标，只有"到达是否均匀"不同。**

**修法因此明确了三条（都需要先改 `docs/ARCHITECTURE.md` 的延迟预算再动代码）**：

| 方案 | 预期效果 | 代价 |
| --- | --- | --- |
| 抬缓冲上限 80 → 150 ms | 能盖住两轮观察到的最大尖峰（180 ms 那次仍会漏） | 端到端延迟 +70 ms，与"p95 ≤ 150 ms"的预算冲突 |
| 改连接参数（更小的 interval / 更长的 peripheral latency） | 从源头减少到达抖动 | 功耗上升；设备侧要重新验证 6 个连接参数的退避逻辑 |
| 在 `Playout` 里加"到达抖动感知"的自适应 | 抖动大时临时多存一点 | 需要重新设计自适应控制器（现在只在欠载后才抬目标，且已顶到上限） |

**G2 仍记 FAIL**，但它现在是一条**有明确根因、有可选修法**的 FAIL，
不再是"不知道为什么会欠载"。

## KI-007：电量计读到 `SOC=0 / VCELL=0`，插着 USB 也不涨

> 状态：**算法错误已修，物理原因未定。** 2026-11-06 现场。

### 现象

GUI 顶栏显示「电量 0%，请充电」，而设备正插在电脑的 USB 口上。用户的第一反应是
"明明连着电脑，怎么提示充电"。

### 已经查实的

| 事实 | 怎么得到的 |
| --- | --- |
| 设备**确实**在报 0，不是界面算错 | 串口日志 `首次读数 0%；reg00-07 = A0 00 00 00 00 00 00 00` |
| 电量计芯片在、I2C 通路正常 | `reg00`（VERSION）= `0xA0`，非零；读寄存器有 ACK |
| 电芯电压也是 0 | `VCELL`（`0x02/0x03`）= `0x0000`，按 305.2 µV/LSB 折算是 0 mV（系数未真机核对） |
| SOC 换算错了 100 倍 | 旧代码 `buf[0]*100 + buf[1]*100/256`；`0x04` 是整数 %、`0x05` 是 1/256 %，两者并列，不该乘 100 |

### 为什么之前"一直满电、突然没电"

11-06 02:57 的日志里，电量是 `97 → 94 → 93 → … → 0`，每秒约 2%。按旧公式反推，
真实值是 `0.97% → 0.00%`——整数部分 `0x04` 一直是 0，只有小数部分在动。
也就是说**整晚真实电量都在 1% 以下，界面却因为放大 100 倍撞上 100% 上限一直显示"满电"**，
直到 03:09 电量耗尽、设备掉电。这不是"电量突然跳水"，是"界面从来没说过真话"。

### 仍然未知的

`VCELL = 0` 有三种解释，目前分不出来：

1. **电池包没接上 / 连接器松了**：设备靠 USB 供电照样能跑。
2. **保护板已锁死**：03:09 那次深度放电可能让锂电保护板过放锁定，输出端 0 V，
   充电 IC 也充不进去——这与"关机链路正常、插着电也永远是 0%"吻合。
3. **电量计的这一路测量本身坏了**，或本板 CW2017 的 VCELL 输入没接。

### 下一步（按顺序，第 1 步就能定案）

1. **用万用表量电池两端电压**（拆机，量保护板输出）：
   - 3.0–4.2 V → 电池是好的，问题在电量计或固件（查 VCELL 引脚与寄存器）。
   - 0 V → 走第 2、3 步。
2. 关机状态下插 USB 充 1–2 小时（绿灯常亮），再开机看 `reg00-07`。
   开机边跑边充时净充电电流很小，不能用来判断"能不能充进去"。
3. 若仍为 0 V：换一块电池包复测。电芯已被过放到 0 V 时不要指望它自己恢复。

### 影响与口径

- **电量数字暂时不能当验收数据**，也不能据此判断"还能录多久"。
- 设备处于 0% 时不要做长时间测试：随时可能掉电，会把"毛刺/欠载/断连"这类
  测试结论污染成假数据（KI-001 / KI-005 / KI-006 复测前先确认电量）。
- 固件现在会在**首读**打一条带寄存器转储的 INFO（`apm_battery`），
  下次现场直接看这一行，不用再猜。

### 2026-11-06 11:20 追加证据（排除"芯片在睡觉"）

固件加了开机全寄存器转储后，实测：

```text
reg00-0F = A0 00 00 00 00 00 00 00 F0 00 40 14 AA 50 00 00
```

| 寄存器 | 值 | 结论 |
| --- | --- | --- |
| `0x00` VERSION | `A0` | 芯片在，I2C 通路正常 |
| `0x02/0x03` VCELL | `00 00` | 电芯端测量值就是 0 V（不是精度问题，是 0） |
| `0x04/0x05` SOC | `00 00` | SOC 也确实是 0 |
| `0x08–0x0F` 配置区 | `F0 00 40 14 AA 50 00 00` | 非全零 → 芯片有配置，不是"没初始化" |
| `0x0A` MODE | `40` | **不是睡眠态的 `0x30`** → 排除"芯片在睡觉所以读数全 0" |

固件里保留了这个转储（`apm_battery: reg00-0F = ...`），只在开机打一次；
另外 VCELL 持续为 0 时每分钟补一条 warn、最多 5 条，用来观察"插着电到底有没有在涨"。

**结论不变，但更硬**：芯片活着、有配置、不在睡眠，却测到电芯 0 V —— 只能是电池包这一侧
断路（没接牢 / 保护板锁死 / 电芯已放废）。这三者软件都无能为力，**必须动万用表或换电池**。

### 2026-11-06 11:50 根因定位，上面那条结论作废

上一条把 `0x0A = 0x40` 读成"不是睡眠态"，**这一步错了**。查 CW2017 官方 datasheet
（CellWise，寄存器映射见下表）才发现：**CW2017 的 0x0A 是 `INT_CONF`，不是 MODE**；
`0x0A MODE`、`0x06 RRT`、`写 0xAA 触发重算` 全是 **CW2015** 的布局，两代并不通用。

| 地址 | CW2015 | **CW2017（本板）** | 上电默认 |
| --- | --- | --- | --- |
| `0x00` | VERSION | VERSION | `0xA0` |
| `0x02/0x03` | VCELL | VCELL（312.5 µV/LSB） | `0x0000` |
| `0x04/0x05` | SOC | SOC | `0x0000` |
| `0x06` | RRT | **TEMP**（只读） | `0x00` |
| `0x08` | CONFIG | **CONFIG**（默认 `0xF0` = sleep） | `0xF0` |
| `0x0A` | MODE | **INT_CONF** | `0x40` |
| `0x0B` | SOC_ALERT | SOC_ALERT | `0x14` |
| `0x0C` | TEMP_MAX | TEMP_MAX | `0xAA` |
| `0x0D` | TEMP_MIN | TEMP_MIN | `0x50` |

现场那行 dump `A0 00 00 00 00 00 00 00 F0 00 40 14 AA 50 00 00`，逐字节就是
**出厂默认值全集**：`0x08 = F0`、`0x0A = 40`、`0x0B = 14`、`0x0C = AA`、`0x0D = 50`。
也就是说芯片从上电到现在**一次都没被正确初始化过**，一直停在 sleep。

而 CW2017 datasheet 的 "Power State" 写得很清楚：上电默认 sleep，sleep 下
**VCELL / SOC 读出来全是 0**，退出要两步——**写 `0x30` 到 `0x08` 清 sleep，再写 `0x00` 到 `0x08` 清 restart**。

旧固件做的是：写 `0xAA` 到 `0x06`（CW2017 这里是只读的 TEMP，写了等于没写），
再读 `0x0A` 判断是否等于 `0x30`（`INT_CONF` 默认 `0x40`，永远不成立）→ **唤醒分支从未执行**。

所以：**不是电池包断路，不是保护板锁死，是电量计没醒。** 界面上的"0%，请充电"是
sleep 态的寄存器值，不是电芯的真实状态。

已改（`device/main/battery.c`）：

- 唤醒改成 datasheet 的两步写 `0x08`（`0x30` → `0x00`），随后等 200 ms 让 FastCali 出首估；
- 开机日志多打一条「唤醒后 VCELL raw / mV / SOC」——`0x08` 从 `F0` 变 `00` 且 VCELL 非 0
  就说明唤醒成功，一眼可判，不用再猜；
- 读电量改成一次连读 `0x02–0x05`：**VCELL 与 SOC 同时为 0 时返回"不可用"而不是报 0%**，
  避免再把"测不到"显示成"没电了，请充电"；
- VCELL 换算从 CW2015 的 305.2 µV/LSB 改成 CW2017 的 312.5 µV/LSB。

**仍未验证**：烧录后的实际读数、唤醒能否稳定、充电时 SOC 是否正常上涨。这一步必须上真机看
`apm_battery: 唤醒后 VCELL ...` 那一行。

### 2026-11-06 14:03 真机结果：唤醒成功，电池其实是**满的**

烧录后实测（MAC `98:c3:77:f6:c6:44`）：

```text
apm_battery: cal: reg00-0F = A0 00 00 00 00 00 00 00 00 00 40 14 AA 50 00 00
apm_battery: 读法 1/3：VER[1B]=A0 | VCELL[2B]=0000 | SOC[2B]=0000
apm_battery: 读法 2/3：VER[1B]=0F | VCELL[2B]=336B | SOC[2B]=FF00
apm_battery: 读法 3/3：VER[1B]=0F | VCELL[2B]=336B | SOC[2B]=FF00
```

| 结论 | 依据 |
| --- | --- |
| **唤醒生效** | `0x08` 从 `F0` 变 `00`，`0x0A` 仍是默认 `40`（INT_CONF） |
| **电池满电，不是过放** | VCELL `0x336B` = 13163 × 312.5 µV ≈ **4113 mV**，满电锂电的典型值 |
| **之前读到 1.0 V 是固件算错** | VCELL 高字节 `0x02` 只有低 6 位是数据，旧代码 `>> 2` 多除以 4，4.11 V 被读成 1.03 V |
| **电压稳定不涨＝已充满停充** | 7 分钟内 raw 恒定（3253），插着 USB 也不上升 |
| **SOC 仍是无效值** | `0xFF00`（255%），两种读法（2 字节连读 / 单字节分读）结果一致，不是读法问题 |

### 修正

1. VCELL 解析：`(((hi << 8) | lo) >> 2)` → `(((hi & 0x3F) << 8) | lo)`，全文件 5 处。
   `>> 2` 是把"低 6 位对齐"当成了"16 位左移 2 位"，整整差 4 倍。
2. 唤醒流程按 CW2017 datasheet：`0x30` → `0x00` 写 `0x08`（已验证生效）。
3. 读电量时 VCELL 与 SOC 同时为 0 才算"不可用"；SOC > 100 也算不可用（不报 0%，不提示充电）。
4. 日志口径改成「电量不可用（…）：VCELL=xxxxmV」，并且**不再写"读数失败…维持 0%"**——
   那句话会让人以为电量真的为 0。

### 已定位（2026-11-06 17:58）：BATINFO 全 0，芯片里没有电池 profile

当时的三个猜测保留在这里，因为第一个就是真因，后两个被真机结果否掉：

1. **CW2017 的电池 profile 没烧 / 不匹配** ← **就是这条**
2. 芯片从上电起没做过一次完整充放电，`FastCali` 给不出首次估算 ← 不是：写入 profile 后
   2.6 s 就出 `77%`，不需要充放电循环
3. 写 `CONFIG=0x00` 动了配置位 ← 不是：CONFIG 读回 `0x00`，VERSION `0x0F`，都在正常运行态

真机日志（`device/main/battery.c`，2026-11-06 17:54）：

```text
I (311) apm_battery: BATINFO 修复前 10-1F = 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00
I (312) apm_battery: BATINFO 修复前 20-2F = 00 00 ... （30/40/50 段同样全 0）
W (315) apm_battery: BATINFO 修复前：全 0（未写入 profile）
W (316) apm_battery: BATINFO 与官方 profile 不一致：按缺失处理，开始写入
I (357) apm_battery: profile 已写入并回读校验通过，重启芯片加载
I (988) apm_battery: 唤醒后 VCELL raw=12660 ≈3956mV，SOC=255%   ← 刚重启，FastCali 还没算完
I (2597) apm_battery: 首次读数 77%；reg00-07 = 0F 00 31 76 4D 4B 8F 00；VCELL≈3956mV，TEMP=143
```

`TEMP=0x8F` 按 datasheet `-40 + 143/2 = 31.5 °C`，室温合理——芯片的 ADC 与温度通道都正常，
只有 SOC 因为缺 profile 而无解。

### 修法（已落地并真机验证）

`device/main/battery.c` 增加 `profile_matches` / `profile_install`：

- 开机把 BATINFO 与随固件的**官方优特利 UTL 520 mAh profile**（来自 FoloToy 上游 BSP
  `components/bsp/src/bsp_battery.c`，commit `7eeb76d`）逐字节比对；
- 不一致才写：`CONFIG=0xF0`（sleep）→ 逐字节写 `0x10–0x5F` → 回读校验 → 置 `0x0B`
  的 UPDATE 位（`0x80`）→ `0x30 → 0x00` 重启加载；
- 读失败或校验不过**不写/不置位**：宁可继续报"不可用"，也不要让芯片带着半份 profile 算错。

**幂等验证**（2026-11-06 17:56，第二次开机）：`BATINFO 与官方 UTL 520mAh profile 一致，
无需写入`，2.5 s 读到 `79%`。不会每次开机重写 80 字节。

**BLE 与界面验证**：`apmctl battery` → `电量 77%`；GUI 顶栏 → `电量 77%`（自动连接场景，
靠 `AppSnapshot.battery_pct` 回填，见 KI-009）。

**顺带排除的两件事**：

- **不是电池没接**：4.11 V 是真实电芯电压，CELL 引脚测得准。
- **不是"充电中"**：满电后充电 IC 停充，电压稳定在 4.07–4.11 V，这是"已充满"的特征，
  不是"正在充电"（充电中会看到 4.15–4.2 V 的恒压段）。

### 2026-11-06 14:06 最终版日志（已烧录）

```text
apm_battery: VERSION 第 1 次：OK，值 0x0F
apm_battery: reg00-0F = 0F 00 33 6C FF 00 00 00 00 00 40 14 AA 50 0F F3
apm_battery: 唤醒后 VCELL raw=13164 ≈4113mV，SOC=255%
apm_battery: 读法 1/3：VER[1B]=0F | VCELL[2B]=336C | SOC[2B]=FF00 | SOC[1B×2]=FF/00
apm_battery: 读法 3/3：VER[1B]=0F | VCELL[2B]=336C | SOC[2B]=FEE8 | SOC[1B×2]=FE/E8
apm_battery: 电量不可用（ESP_ERR_INVALID_RESPONSE）：VCELL=4113mV，从未读到过有效电量
```

**VCELL 稳定在 4.113 V，SOC 在 `0xFF00 ↔ 0xFEE8` 之间缓慢变化**——芯片在算，只是结果落在
无效区间。注意 `reg00` 这次读出 `0F`（上次 16 字节连读是 `A0`）：**读 0x00 这个地址的结果
不稳定**，`0x0E/0x0F`（VOLT_ID）也在 `00 00 ↔ 0F F3` 之间跳。这两个都只影响诊断打印，
不影响 VCELL / SOC 的读取（`0x02–0x05` 两种读法结果一致）。

**因此：VERSION 不应作为"芯片在不在"的判据**，判据应该是 VCELL 能否读出非 0 值。

## KI-008：GUI 连接卡在「连接中」，电量特征值回 ATT 错误把 `read` 挂住

> 状态：**已修并真机验证（2026-11-06 14:59）。** 这是 KI-007 的连带伤害。

### 现象

打开 GUI，日志停在两行就没了，界面「连接中」永远不结束：

```text
ble: 检测蓝牙适配器
ble: 自动连接上次设备：AI Passport Mic
app: 状态 idle → connecting
ble: 连接 225373d2-7633-3dcc-fb93-fa878c4f902a     ← 之后一行不再写
```

`CONNECT_TIMEOUT`（10 s）+ `ADAPTER_PROBE_TIMEOUT`（6 s）应该 16 s 就超时报错，但**等了 4 分钟也没有**。
表现上还带一个副作用：**设备不再广播**，`apmctl scan` 扫不到它，CLI 也连不上——因为它已经被连上了。

### 定位

设备端串口日志给出了决定性证据——**连接和订阅全都成功了**：

```text
apm_link: 已连接 conn=1 itvl=30 ms
apm_link: MTU = 247（音频块需要 >= 168）
apm_link: 订阅: audio=0 status=1 event=1
apm_link: 订阅: audio=1 status=1 event=1
```

也就是说 `peripheral.connect()` / `discover_services()` / `subscribe()` 都过了，卡在 `Link` 交回
调用方**之后的第一步**——`core.rs` 连接成功后立刻调用的 `link.read_battery()`。

### 根因

设备对 Battery Level（0x2A19）在电量无效时返回的是 **ATT 错误**：

```c
if (s_battery_pct > 100) return BLE_ATT_ERR_UNLIKELY;   // 0xFF 占位 → 回错误
```

**macOS 上 btleplug 的 `Peripheral::read()` 遇到 ATT 错误不返回**（Future 永久 pending）。
而 `read_battery()` 外面没有任何超时，`connect_inner` 的 `tokio::time::timeout` 此时已经结束
（它只包住 `apm_link::connect`），于是整个连接流程就挂在那里。

三个条件同时成立才会踩中：① 电量计没给出有效值（KI-007）；② 设备选择"回错误"而不是回 `0xFF`；
③ PC 端读电量没有超时。

### 修法（双保险）

1. **设备端**：`link.c` 里 0xFF 原样返回，**绝不回 ATT 错误**。
   架构约定本来就是"0xFF / ATT 错误都算不可用"（`ARCHITECTURE.md`），回 0xFF 对两端都安全。
2. **PC 端**：`read_battery()` 加 2 s 超时，超时按 `Ok(None)`（"不可用"）降级。
   电量不是关键路径，读不到也**不能拖住连接**。

### 真机验证（2026-11-06 14:59）

```text
14:59:55 连接 225373d2-...
14:59:58 设备报电量不可用（无 Battery Service 或电量计未就绪）
14:59:58 状态 connecting → ready
14:59:58 已连接并订阅 status/audio/event：AI Passport Mic
14:59:58 起每秒 STATUS 通知正常
```

**3 秒内完成连接**，日志按预期出现「设备报电量不可用」。
（原先这里写的是"顶栏按预期显示「电量不可用」"——11-06 17:25 复核时发现**那句话站不住**：
顶栏当时其实一个字都没有，见 KI-009。日志有结论 ≠ 界面收到结论。）

### 教训

- **故障在两个进程之间时，先看"另一端有没有收到"**：设备端日志说"已连接"，就把嫌疑范围
  一下从"广播/配对"缩到"连接之后的某一步"。
- **兜底超时要包在"会让界面卡住"的那一段**，而不是只包住最外层的函数调用。
  `timeout(connect())` 挡不住 `connect()` 返回**之后**的阻塞。
- 给标准特征值回 ATT 错误要谨慎：规范上没毛病，但主机的实现未必处理得好。

## KI-009：自动连接时顶栏永远没有电量（事件早于监听注册）

> 状态：**已修，2026-11-06 真机复验通过（后端侧）。** 2026-11-06 17:25 现场。

### 现象

设备已连上、日志里明明有「设备报电量不可用」，界面顶栏**一个字都没有**——
不是「电量不可用」，是空白。用户的第一反应是"电量功能根本没做"。

### 根因（三个条件同时成立）

1. `AppSnapshot` **不带电量**：前端唯一的电量来源是 `battery` 事件。
2. GUI 的 `setup` 里 `detect_adapter()` → `auto_connect()`，而前端 `onMounted` 要跑完
   `snapshot()` → `refreshSinks()` → `loadKeymap()` 才注册 `onAppEvent`。
   现场 `auto_connect: true`，自动连接先完成，`Battery` 事件在监听注册之前发出。
3. Tauri 的 `emit` 不重放、不缓存：没有监听者的那一刻，事件直接消失。
   而设备只在**数值变化**时通知；SOC 无效时永远不变，也就**永远不补发**。

于是 `batteryKnown` 恒为 false，`v-if="connectedDevice && batteryKnown"` 恒不成立。

> 补充：这不是"旧包"问题。`target/debug/bundle` 里 14:59 那个包内嵌的前端
> （`index-B7QFluII.js`）已经有「电量不可用」文案，照样空白——因为文案的显示条件
> 是 `batteryKnown`，而它没被置起来。旧 release 包（`index-vLKES92L.js`）是另一层
> 问题：它干脆在 `battery === null` 时就不渲染。

### 修法

- 内核 `Inner` 增加 `battery: Option<Option<u8>>`（`None`=没读过 / `Some(None)`=设备报不可用 /
  `Some(Some(pct))`=有效值）。
- `AppSnapshot` 增加 `battery_pct` + `battery_known`；`snapshot()` 直接回填。
- 连接读完电量、收到 `Notification::Battery`：**先写内核再 emit**；`teardown` 清空。
- 前端 `onMounted` 用 `snap.battery_pct` / `snap.battery_known` 先回填，事件只负责之后的变化。

### 验证

- `cargo test -p apm-app snapshot_carries_battery_verdict` 通过（三种语义都覆盖）。
- `cargo clippy -p apm-app -p apm-gui --all-targets` 0 警告；`vue-tsc` 与 `npm run build` 通过。
- `./scripts/build-gui.sh --release` 出包，`.app` 12.23 MiB、随包固件 720448 字节，
  Info.plist 的蓝牙/麦克风用途声明校验通过。
- **2026-11-06 真机复验 PASS（后端口径）**：release 包，先 `tccutil reset` 清权限、
  预置 `last_device_id` 后冷启动：

  ```text
  21:48:34.473 自动连接上次设备：AI Passport Mic / 状态 idle → connecting
  21:48:35.946 电量 95%          ← 与下一行同一毫秒
  21:48:35.946 状态 connecting → ready
  21:48:36.127 state=1 flags=0x03 sent=30001 dropped=0
  ```

  **电量结论与 `ready` 同毫秒落地**，证明它走的是 `AppSnapshot` 回填而不是事件补发——
  这正是 KI-009 的修法所要保证的。连接耗时 1.47 s。
- **口径限制（别过度声明）**：本轮无屏幕录制权限，**没有截图核对顶栏像素**。
  验到的是"后端在连接时就算出电量并写进快照"，顶栏文字由前端按 `batteryKnown` 渲染。
  要彻底关掉这条，需要在有屏幕权限的机器上看一眼顶栏（或补一条前端单测断言渲染条件）。

### 教训

- **边沿事件不能当唯一真相。** 凡是"连接后一次性算出来的结论"（电量、Profile、
  固件版本……）都要能被快照读到；事件只该承载"变化"。
- 前端注册监听晚于后端动作，是桌面壳里的常见时序，不是偶发竞态。
- 写验收记录时别把"日志里看到了"写成"界面上看到了"——这次差点又骗过自己。
