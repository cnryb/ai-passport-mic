## KI-001：采集端满量程毛刺的根因未定位

**发现时间**：2026-11-04 首轮真机录音。

### 现象

6 次真机录音里有 2 次，在录音进行到 **7.7–8.5 s** 附近出现约 **0.8 s** 的 ±32767
逐样本变号噪声。同一次录音里 `序号跳变丢失 = 0`，即**不是丢块**、不是块头失配。

### 已经排除的

| 假设 | 怎么排除的 |
| --- | --- |
| ADPCM 编码器进入死循环状态 | 把同样的波形喂给 编码→解码：最多污染相邻 1–2 块，之后在静音和低电平底噪下都能自行收敛（`desktop/crates/protocol/tests/glitch_repro.rs` 固化） |
| 丢块导致块头失配 | 同次录音 `序号跳变 = 0`；且解码器每块由块头重置，丢块不会污染后续 |
| 麦克风真实削波 | 削波是平顶、同号连续；这段是逐样本变号（等价 ≥8 kHz 满量程方波），人声与室内噪声做不出这个形状 |
| 断连/重连导致的缓冲残留 | 现象发生在连续录音中段，链路未断，`record` 的丢块与长度异常两项均未增加 |

结论：数据在**进 ADPCM 之前**就已经是垃圾，问题在采集链路（I2S / ES8311）。

### 现在的拦截（不是修复）

两端各拦一次，保证"垃圾不出去"，**但没有解释垃圾为什么产生**：

- **固件**：编码前 `apm_pcm_is_corrupt()` 体检，命中就把整块压成静音并复位预测状态，
  只打串口日志、计数留在设备内存里。
- **PC**：解码后 `apm_protocol::glitch::Suppressor` 再兜一层（静音替换 + 64 样本淡入），
  `record` / `sink` 都过，收尾报告打印"采集端毛刺 N 段，已静音 M 帧"。
- **分析**：`apmctl analyze` 用同一判据扫描，出现即判 `software-fail`，JSON 带
  `glitch_events` / `glitch_ms`。判据口径见 [`SOUND_QUALITY.md`](SOUND_QUALITY.md) 的「毛刺」。

### 仍然未知的

1. **为什么 I2S/ES8311 会读出满量程变号数据。** 候选假设（都还没有证据）：
   codec 时钟瞬态、I2S DMA 半满回调错位或读越界、ES8311 内部软复位、供电跌落导致
   codec 重同步。7.7 s 这个位置是否与某个周期性事件（BLE 连接事件 30 ms、STATUS 心跳 1 s、
   或一次未记录的 gain 写入）对齐，也没查过。
2. **固件压掉的块数没上报。** 只进串口日志，STATUS 载荷仍是 8 字节。要上报得改协议
   （8 → 10 字节）、同步 `ARCHITECTURE.md`、重新生成两端向量。当时判断不值得为诊断字段
   改协议，所以没做 —— 这是取舍，不是遗漏。
3. **真机上出现频率**未知：2/6 是样本太小，没法判断是"偶发"还是"每 8 秒必现"。

### 下一步怎么查（可执行）

1. **抓编码前的原始 I2S 数据。** 在 `audio.c` 的读回调里留一个 100 ms 环形缓冲
   （16 kHz × 4 B × 0.1 s = 6.4 KB，设备无 PSRAM 也放得下），用 `apm_pcm_is_corrupt()`
   命中作为触发，把命中前的快照 + `i2s_channel_read` 返回值 + `esp_timer` 微秒时间戳
   一起输出到串口。这能直接回答"是数字侧还是模拟侧"。
2. **对齐时间轴。** 把抓到的时间戳与 STATUS 心跳、连接事件、按键事件对一遍，
   看毛刺是否总在某个固定周期后出现。
3. **改增益做对照。** 把 PGA 增益降 12 dB 跑 10 分钟：若毛刺仍满量程，更像数字侧
   （DMA / 时钟）；若随增益变小，指向模拟前端或供电。
4. **怀疑 codec 就 dump 寄存器。** 毛刺前后各读一遍 ES8311 的 0x00–0x45，看有没有
   软复位标志或时钟丢失。
5. **统计频率。** 连续 10 分钟录音，记录命中次数与间隔分布，把"2/6"这种样本量补到有意义。

### 验收标准

连续 10 分钟 `apmctl record`：

- `glitch_events == 0`，且串口日志里 `corrupt block` 计数为 0；
- `序号跳变丢失 == 0`；
- 在抓到根因之前，**只允许**在文档里写"已拦截"，不允许写"已解决"。

## KI-002：漂移补偿与毛刺拦截未真机复测

**代码**：`desktop/crates/sink/src/playout.rs`（漂移）、`apm_protocol::glitch`（毛刺）
＋ 固件 `apm_pcm_is_corrupt`。

**已有证据**：

- 漂移：仿真 60 s，−4200 ppm 与 +5000 ppm 两个方向均 0 欠载 / 0 超容量丢弃，
  存量稳定在 61.7 / 79.9 ms，ppm 估计误差 < 400。
- 毛刺：`crates/protocol` 单测 + 合成 WAV（1 段 / 799.6 ms 被正确识别并判 fail）。

**缺的证据**：真机。需要**重新烧录固件**（`apm_pcm_is_corrupt` 在固件侧）后跑：

```bash
./scripts/apmctl-macos.sh sink --to "BlackHole" --seconds 60
```

看收尾两行：

- `漂移: 补偿 ±xxx ppm（补样本 a / 丢样本 b）` —— ppm 应当在 ±5000 以内，
  且 `补/丢` 的样本数与 ppm × 时长对得上；
- `采集端毛刺: N 段 …` —— 若仍出现，说明拦截生效但根因（KI-001）还在。

`缓冲: 目标 …` 那行的欠载次数应为 0（暖机期除外）。

## KI-003：没有声学回环，所以端到端延迟仍无数字

**已经有的**：`apmctl ping`（控制帧 `0x04 PING` / `0x83 PONG`）能测**链路往返时延**，
含两端协议栈、连接间隔、设备任务调度。真机数字还没测（需要烧新固件）。

**仍然没有的**：真正的端到端声学延迟 = 声源 → 麦克风 → codec 采集 → 20 ms 分块 →
BLE → 抖动缓冲 → 声卡播放 → 扬声器。PING/PONG 只覆盖其中"BLE + 两端协议栈"这一段，
**不能**用它替代 M4 的 p95 结论。

**为什么卡住**：`sink --verify` 的回环需要宿主进程有麦克风权限；裸二进制会被 TCC 直接
abort，`apmctl-macos.sh` 的 `.app` 身份目前只声明了蓝牙用途。解法是 G3b：用 GUI 自身的
bundle 身份做回环验收（见 [`GUI.md`](GUI.md)）。

**临时折中**：用外接设备放一段已知脉冲（手机播 1 kHz 短音）录进 WAV，手工对时间轴。
只能给数量级，不能当验收数据。
